## 2. 当前主要问题

1. **类别入口分裂**：品牌使用 `BRAND` + `config/brand_keywords.json`，纸尿裤使用 `DIAPER_LABEL_NAME`，本地目录使用 `LOCAL_LABEL_NAME`，S3 使用 `S3_LABEL_NAME`，后续新类别（例如 `allround_purple`）容易继续复制一套命令。
2. **命令按业务类别硬编码**：`diaper-*`、`brand-s3-*`、`local-dir-*` 等命令中存在大量重复逻辑，且 Web 控制台菜单也按这些固定流程展开。
3. **目录默认值不统一**：当前既有 `datasets/multibrand`、`datasets/diaper_category/<国家>/<版本>`、`datasets/local/<name>`、`datasets/s3/<name>`，也有控制台状态中的 `datasets/allround_purple/GH/v2026-09-17`，目录规则不一致。
4. **Makefile 内存在脚本逻辑**：例如 `makefiles/local-dir/Makefile.mk` 使用 `python -c` 解析路径，部分多项目导出/合并使用较长 shell 循环；后续应转到 Python 脚本中。
5. **Web 控制台类别不可维护**：当前只从品牌库读取 `BRAND` 选项，没有通用“类别列表”的增删改、多选与持久化能力。
6. **文档与架构会过期**：如果改为通用类别体系，`设计.md`、`README.md`、各 makefiles README、`scripts/README.md` 需要同步更新。
7. **Git 忽略规则需要重整**：需要明确“过程产物不进 Git，结果配置/类别列表/可复现文档进 Git”，并避免误提交大图片、权重、临时日志和私密配置。

## 3. 目标设计

### 3.1 通用标签类别目录

新增可提交 Git 的通用类别配置，例如：

```text
config/label_categories.json
```

建议结构：

```json
{
  "description": "YOLO/Label Studio/OCR/EC2 通用标签类别配置。",
  "sets": [
    {
      "name": "brands",
      "display_name": "品牌包装",
      "description": "历史多品牌包装识别类别。",
      "task_type": "detection",
      "classes": [
        {
          "class_id": 0,
          "name": "SOFTCARE",
          "class_name": "softcare",
          "aliases": ["SOFT CARE"],
          "enabled": true
        }
      ]
    },
    {
      "name": "general",
      "display_name": "通用陈列类别",
      "description": "用户可在本地控制台维护的通用类别集合。",
      "task_type": "detection",
      "classes": []
    }
  ]
}
```

规则：

- `LABEL_SET`：选择类别列表，例如 `brands`、`general`、未来用户自定义列表。
- `LABELS`：在当前类别列表内多选类别；为空或 `all` 表示使用该列表全部启用类别。
- `class_id`：有显式值时保持稳定；没有显式值时按顺序补齐。
- `class_name`：用于 YOLO YAML、目录 slug、模型输出；若未填写则由 `name` 自动生成。
- `aliases`：保留给 OCR/YOLO-World 文本提示词和标签匹配。
- 旧 `config/brand_keywords.json` 初期作为兼容输入或迁移来源；后续文档声明新流程以 `config/label_categories.json` 为准。

### 3.2 通用目录规则

新增公共参数：

```makefile
COUNTRY ?= default
DATA_VERSION ?= v$(shell date +%Y-%m-%d)
LABEL_SET ?= brands
LABELS ?= all
DATASET_NAME ?= 自动根据 LABEL_SET + LABELS 生成，也允许用户覆盖
```

默认目录改为国家/版本分层，并允许参数覆盖：

```text
datasets/<数据来源或流程>/<COUNTRY>/<DATA_VERSION>/<DATASET_NAME>/
```

示例：

```text
datasets/excel/CI/v2026-09-18/brands_all/
datasets/local/GH/v2026-09-17/allround_purple/
datasets/s3/GH/v2026-09-17/allround_purple/
outputs/ec2/s3/GH/v2026-09-17/allround_purple/<EC2_RUN_NAME>/
models/ec2/s3/GH/v2026-09-17/allround_purple/<EC2_RUN_NAME>/best.pt
```

保留所有 `*_ROOT`、`*_YAML`、`*_MANIFEST` 这类参数覆盖能力，确保上传/下载目录可由用户自行设定，不再依赖写死目录。

### 3.3 通用脚本能力

新增或改造以下脚本：

1. `scripts/common/label_catalog.py`
   - 读取 `config/label_categories.json`。
   - 兼容旧 `brand_keywords.json`。
   - 支持 `LABEL_SET` + `LABELS` 多选过滤。
   - 输出 YOLO names、Label Studio XML、OCR aliases、slug/dataset name。

2. `scripts/config/label_profile.py`
   - 替代 `brand_profile.py` 在 Makefile 中计算 `DATASET_NAME`、`LABEL_FILTER`、`available-labels` 等。
   - 后续 `brand_profile.py` 可保留为兼容薄封装。

3. `scripts/config/write_label_yolo_yaml.py`
   - 替代 `write_brand_yolo_yaml.py` 和 `write_single_class_yolo_yaml.py` 的核心逻辑。
   - 支持单类别和多类别 YAML。

4. `scripts/label_studio/generate_label_import.py`
   - 统一生成无预标注 LS 导入 JSON。
   - 支持 Excel 下载报告、本地图片目录、S3 图片清单三类来源的可复用逻辑。

5. `scripts/label_studio/export_labels_to_yolo.py`
   - 统一 LS 导出转 YOLO，支持单类别和多类别。

6. `scripts/label_studio/export_and_merge_projects.py`
   - 把 Makefile 中的多项目导出/合并 shell 循环迁入 Python。
   - Makefile 只传参数和调用脚本。

7. `scripts/config/resolve_path.py` 或在通用 profile 中输出路径
   - 替代 Makefile 中的 `python -c` 内联片段。

说明：旧脚本可先保留为兼容入口，但内部尽量调用通用模块，避免遗漏旧功能。

### 3.4 Makefile 整合方案

新增通用模块，例如：

```text
makefiles/label-workflow/Makefile.mk
```

核心命令建议：

```text
label-list                         # 显示类别列表和类别
label-yaml                         # 按 LABEL_SET/LABELS 生成 YOLO YAML
1-excel-workflow-to-ls             # Excel 图片下载 -> 通用类别 LS
1-local-workflow-to-ls             # 本地目录 -> 通用类别 LS
1-s3-workflow-to-ls                # 本地目录 -> S3 -> 通用类别 LS
2-label-workflow-after-ls          # LS 导出 -> YOLO 训练集
2-label-merge-projects-to-yolo     # 多 LS 项目合并 -> YOLO
3-label-ec2-upload-data            # 上传本地 YOLO 数据集到 EC2
3-s3-workflow-ec2-train            # 上传 S3 manifest/labels/YAML -> EC2 下载图片并训练
label-ec2-train
label-ec2-evaluate
label-ec2-download-artifacts
label-ec2-download-model
```

兼容策略：

- 旧 `diaper-*`、`local-dir-*`、`brand-s3-*`、品牌 OCR/YOLO-World 命令先不立即删除，避免功能遗漏。
- 旧命令改为调用通用命令或保留为别名，并在 README 中标记“兼容入口，推荐使用通用 label-* 命令”。
- Makefile 中不再新增长 shell/Python 片段；复杂逻辑全部放脚本。

   - 使用 `LABELS` 多选类别；默认全选/`all`。

   - 类别管理
   - 图片来源 / 标注准备：Excel、本地目录、S3、OCR/预标注、导入 LS

4. 持久化：
   - `config/label_categories.json`：类别定义，提交 Git。
   - `web-console/state.json`：本地控制台参数缓存/收藏。按用户要求允许提交 Git，但会先清理明显敏感或临时字段，避免提交私钥路径、临时 token 等。

### 3.6 `.gitignore` 优化原则

按“过程不要 Git，结果要 Git”整理：

- 继续忽略：
  - 大图片、训练集图片、raw、pseudo 图片。
  - 权重模型：`*.pt`、`*.onnx`、`*.pth`。
  - 临时目录：`.tmp/`、`logs/`、`.label-studio-data/`、`.pytest_cache/`、`__pycache__/`。
  - 私密配置：`.env`、`config/*local*.yaml`、AWS/EC2 密钥相关文件。
- 允许提交：
  - `config/label_categories.json`。
  - `config/generated/.gitkeep` 等目录占位。
  - `docs/plans/*.md`、README、设计文档。
  - 必要的非敏感控制台持久化结果（例如空白或清理后的 `web-console/state.json`）。
- 对 `datasets/**/metadata`、`labels`、`label_studio` 等结果产物分层处理：默认仍忽略过程产物；如果确认为可复现实验结果，需要通过精确 `!` 规则或单独导出到 `docs/reports/`。

## 5. 我的建议

1. **不要删除旧命令，先做兼容别名**：本次改动范围大，直接删旧命令容易漏功能。先让旧命令走通用逻辑，README 中推荐新命令，稳定后再清理。
2. **类别配置作为代码资产提交**：`config/label_categories.json` 应纳入 Git，这比把类别散落在 Make 参数、控制台缓存或私有配置中更可复现。
3. **控制台 state 只提交非敏感默认值**：参数缓存可提交，但应避免把私钥路径、临时 token、个人机器路径等敏感/强本地化内容长期写入 Git。
4. **目录一律显式可覆盖**：默认用 `COUNTRY/DATA_VERSION/DATASET_NAME`，但所有上传、下载、训练、归档目录仍允许参数覆盖，适配历史数据。
5. **测试先覆盖纯逻辑和 dry-run**：真实训练、真实上传下载成本高且依赖环境，默认以单元测试、临时 fixture、dry-run 命令和控制台 API 冒烟测试作为完整回归基线。
